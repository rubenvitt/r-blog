De meeste AI-demo's stranden niet op het model. Ze stranden op het feit dat ze vrije tekst produceren - terwijl de applicatie eigenlijk contracten nodig heeft. Zodra een model niet meer alleen vriendelijk antwoordt in een chatvenster, maar productlogica in gang zet, zijn goede prompts alleen niet meer genoeg.

AI FullStack Engineering begint waar modeloutput een onderdeel van het systeem wordt - dus daar waar ik contract, evaluatie en observability nodig heb.

## De voorbereiding: ons voorbeeld

Om het allemaal wat concreter te maken, begin ik met een voorbeeld: een mini-webapp die een GitHub-issue of willekeurige tickettekst (bijv. uit Jira of GitLab) omzet in een gestructureerd implementatieplan. Daarvoor gebruik ik eerst een doelstructuur, aan de hand waarvan ik een AI-FullStack-feature uitleg.

```json
  "risks": ["string"],
  "implementationSteps": ["string"],
  "testIdeas": ["string"],
  "requiresApproval": true

```

Op basis van dit voorbeeld is het eenvoudig om een webapp te laten bouwen die met behulp van dit doelbeeld verschillende implementatieplannen zinvol weergeeft - dat heeft in dit geval Claude Code voor me gedaan.

## Contract-first in plaats van prompt-first

Met het voorbeeld hierboven heb ik Claude gewoon alles laten bouwen - eigenlijk zijn we hier al klaar. De app werkt (na een door ChatGPT geschreven prompt).

<Accordion title="Gegenereerde prompt voor het bouwen van de demo">
You are a senior TypeScript engineer. Build a small but polished demo web app that showcases schema-first AI output using the Vercel AI SDK.

Do not ask follow-up questions.
Make reasonable choices and implement the full app end-to-end.
Do not leave placeholders or stubs.
Keep the code compact, readable, and suitable for a public demo repo / blog post.

Goal

Build a mini web app that turns either:

- freeform story / ticket text
- a GitHub issue

into a structured implementation plan.

The point of the app is to demonstrate that the AI feature is contract-first, not chat-first.

Stack

Use:

- Next.js App Router
- TypeScript
- AI SDK
- AI SDK UI
- Zod
- @ai-sdk/openai
- minimal styling only (simple CSS or Tailwind is fine)
- no database
- no authentication system
- no server-side persistence

Non-negotiable AI SDK architecture

Use these exact patterns:

- shared Zod schema imported by both client and server
- streamText + Output.object(...) in the route handler
- experimental_useObject on the client
- createOpenAI(...) to instantiate the provider with a request-specific API key
- custom request headers from the client to the analyze route
- no plain-text fallback mode for the main analysis flow
- do not use useChat for the main experience

This app is object-generation first, not chat first.

Core JSON contract

The app must use this exact top-level JSON shape and these exact property names:

{`{
"summary": "string",
"affectedAreas": ["frontend", "backend", "database", "infra"],
"risks": ["string"],
"implementationSteps": ["string"],
"testIdeas": ["string"],
"requiresApproval": true
}`}

Implement it as a shared Zod schema and export the inferred TypeScript type.

Schema requirements:

- summary: non-empty string
- affectedAreas: non-empty array of unique enum values, restricted to: frontend, backend, database, infra
- risks: array of strings
- implementationSteps: non-empty array of strings
- testIdeas: non-empty array of strings
- requiresApproval: boolean

Do not parse model text with regex.
Do not accept "almost matching" output.
The UI and server must rely on schema-validated structured output.
</Accordion>

Maar laten we een paar stappen teruggaan. Normaal gesproken bouw ik niet iets alleen om het met AI te vullen. In plaats daarvan wil ik mijn gegevens laten verwerken en slim in de UI laten integreren. Daar zijn al talloze artikelen over op internet te vinden, en AI helpt me daar al prima bij.

Het kernpunt is echter: eerst komt het contract, dan de prompt. Ik moet weten welke gegevens ik gestructureerd moet extraheren, voordat ik aan het schrijven en perfectioneren van mijn prompt begin. Daarvoor moet ik engineeringwerk op een rij zetten dat ook in het pre-AI-tijdperk al bekend had moeten zijn.

- Welke velden wil ik uit de ongestructureerde gegevens halen?
- Welke velden zijn verplicht? Welke optioneel?
- Welke waardebereiken gelden voor getallen & strings? Zijn er enums?
- Waar moet ik de output begrenzen, zodat hij in de UI of pipeline bruikbaar blijft?

Afhankelijk van de gekozen programmeertaal helpen verschillende frameworks me daarbij. Denken we aan een van de modernere ontwikkelomgevingen (TypeScript), dan zou bijvoorbeeld ai-sdk in aanmerking komen. Maar ook voor Java is er iets: Spring AI, en andere programmeertalen hebben ongetwijfeld vergelijkbare tooling. Deze frameworks helpen de communicatie met verschillende model providers te uniformeren, zodat ik me niet direct aan leveranciers en hun API's hoef te binden. In dit artikel concentreer ik me op TypeScript & ai-sdk.

<LinkCard url="https://spring.io/projects/spring-ai" />

Zulke frameworks hebben het grote voordeel dat ze de API's van de afzonderlijke aanbieders uniformeren en typische functies eenvoudig en gelijkwaardig configureerbaar houden - bijvoorbeeld structured outputs, precies wat we nodig hebben.

<LinkCard url="https://ai-sdk.dev/docs/agents/building-agents#structured-output" />

Om dit contract op te stellen, is meestal een contract - vooral JSON Schema - nodig. JSON Schema's beschrijven het contract voor JSON: welke velden zijn verplicht? Aan welke regex moeten die waarden voldoen? Getalbereiken enz. - om dit JSON Schema te maken of te valideren kunnen we tools gebruiken zoals [https://json.ophir.dev/](https://json.ophir.dev/). Of AI vragen om een passend JSON Schema voor onze behoeften te maken.

> Het belangrijkste deel van mijn AI-feature is niet de prompt, maar het contract dat de rest van de applicatie van het modelantwoord verwacht.

Met het gegenereerde of zelf gemaakte contract op zak kunnen we aan de slag met een passende prompt. Het antwoord zal dan óf aan het contract voldoen - óf aan een fout-contract dat we apart moeten afhandelen, bijv. `refusal` van OpenAI.

## Evals in plaats van onderbuikgevoel

> Wie een AI-feature bouwt zonder evals, test op de gebruiker.

40 regels resultaat. LGTM. Done.

Of... niet?

> De vraag is niet of het antwoord "slim" klinkt, maar of het betrouwbaar genoeg is voor mijn workflow.

Hoe weet ik dat het resultaat een goed resultaat is? Hoe weet ik dat ik erop kan vertrouwen? Het contract geeft me een structurele garantie. Of de inhoud vakinhoudelijk deugt, is daarmee nog niet beantwoord. Daarom moeten vooral de inhoudelijke vragen beantwoord worden: zijn de betrokken gebieden zinnig herkend? Zijn de risico's bruikbaar? Kan ik echt iets met de testideeën - of is het overbodige onzin? Is de approval-flag plausibel?
Eén manier om deze vragen volledig te beantwoorden is door elk afzonderlijk antwoord heen te gaan - en die vragen voor mezelf beantwoorden en beoordelen. Daarna kan ik de prompt aanpassen en opnieuw beoordelen. Maar mijn eerlijke mening daarover? Dat wil ik niet, nee! Ik heb er geen zin in.

En ja, er is een alternatief. Zelfs meerdere. OpenAI heeft een eigen optimizer, maar er zijn ook talloze open-source tools. Een voorbeeld daarvan is [https://github.com/promptfoo/promptfoo](https://github.com/promptfoo/promptfoo).

## Observability in plaats van een black box

Als we niet-deterministische systemen in onze applicaties inbouwen, is het des te belangrijker om te begrijpen wat er gebeurd is als er iets kapotgaat, zodat we een manier vinden om precies dat te mitigeren. Daar horen een paar belangrijke datapunten bij die we het liefst willen verzamelen:

- welk model is gebruikt?
- hoe lang had het LLM nodig voor een antwoord?
- was de teruggegeven JSON geldig volgens het contract?
- waren retries nodig?
- eventueel: welke tools zijn gebruikt?
- waar moesten mensen ingrijpen?
- hoeveel tokens zijn er gebruikt en hoe hoog waren de bijbehorende kosten?

OpenTelemetry heeft inmiddels conventies voor GenAI-applicaties voor events, metrics & spans. Dat betekent dat ook de AI-functies in de observability kunnen worden opgenomen. In de eerder genoemde AI SDK bestaat ook een connector om via het framework automatisch de bijbehorende data vast te leggen en te versturen.
