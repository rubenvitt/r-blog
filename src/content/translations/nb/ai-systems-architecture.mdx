De fleste AI-demoer feiler ikke på grunn av modellen. De feiler fordi de produserer fritekst - selv om applikasjonen egentlig trenger kontrakter. Så snart en modell ikke lenger bare svarer pent i et chatvindu, men utløser produktlogikk, holder det ikke lenger med gode prompts alene.

AI FullStack Engineering begynner der modelloutput blir en del av systemet - altså der jeg trenger contract, evaluering og observability.

## Forberedelsen: eksemplet vårt

For å gjøre alt dette litt mer konkret vil jeg begynne med et eksempel: en mini-webapp som gjør et GitHub-issue eller en hvilken som helst ticket-tekst (f.eks. fra Jira, GitLab) om til en strukturert implementeringsplan. Utgangspunktet er en målstruktur som jeg bruker til å forklare en AI-FullStack-feature.

```json
{
  "summary": "string",
  "affectedAreas": ["frontend", "backend", "database", "infra"],
  "risks": ["string"],
  "implementationSteps": ["string"],
  "testIdeas": ["string"],
  "requiresApproval": true
}
```

Med dette eksemplet som utgangspunkt er det lett å få laget en webapp som bruker dette målbildet til å vise ulike implementeringsplaner på en fornuftig måte - det tok Claude Code seg av for meg i dette tilfellet.

I webappen som ble laget, kan brukeren lime inn et issue i tekstfeltet eller hente det fra GitHub - og få det vist strukturert. Klart, dette er et veldig enkelt og raskt oppdiktet use case, men prinsippene og konseptene jeg forklarer, gjelder også for mer gjennomarbeidede UI-er - her er de bare lette å følge.

## Contract-first i stedet for prompt-first

Med eksemplet over lot jeg Claude lage alt i én omgang - egentlig er vi allerede ferdige her. Appen fungerer (etter en prompt laget av ChatGPT).

<Accordion title="Generert prompt for å lage demoen">
You are a senior TypeScript engineer. Build a small but polished demo web app that showcases schema-first AI output using the Vercel AI SDK.

Do not ask follow-up questions.
Make reasonable choices and implement the full app end-to-end.
Do not leave placeholders or stubs.
Keep the code compact, readable, and suitable for a public demo repo / blog post.

Goal

Build a mini web app that turns either:

- freeform story / ticket text
- a GitHub issue

into a structured implementation plan.

The point of the app is to demonstrate that the AI feature is contract-first, not chat-first.

Stack

Use:

- Next.js App Router
- TypeScript
- AI SDK
- AI SDK UI
- Zod
- @ai-sdk/openai
- minimal styling only (simple CSS or Tailwind is fine)
- no database
- no authentication system
- no server-side persistence

Non-negotiable AI SDK architecture

Use these exact patterns:

- shared Zod schema imported by both client and server
- streamText + Output.object(...) in the route handler
- experimental_useObject on the client
- createOpenAI(...) to instantiate the provider with a request-specific API key
- custom request headers from the client to the analyze route
- no plain-text fallback mode for the main analysis flow
- do not use useChat for the main experience

This app is object-generation first, not chat first.

Core JSON contract

The app must use this exact top-level JSON shape and these exact property names:

{`{
"summary": "string",
"affectedAreas": ["frontend", "backend", "database", "infra"],
"risks": ["string"],
"implementationSteps": ["string"],
"testIdeas": ["string"],
"requiresApproval": true
}`}

Implement it as a shared Zod schema and export the inferred TypeScript type.

Schema requirements:

- summary: non-empty string
- affectedAreas: non-empty array of unique enum values, restricted to: frontend, backend, database, infra
- risks: array of strings
- implementationSteps: non-empty array of strings
- testIdeas: non-empty array of strings
- requiresApproval: boolean

Do not parse model text with regex.
Do not accept "almost matching" output.
The UI and server must rely on schema-validated structured output.
</Accordion>

Men la oss gå noen steg tilbake. Normalt bygger jeg ikke noe bare for å fylle det med AI. Poenget er at dataene mine skal bearbeides og integreres intelligent i UI-et. Det finnes allerede utallige artikler om det på nettet, og AI hjelper meg utmerket med det.

Kjernepoenget er likevel: Først kommer contracten, så prompten. Jeg må vite hvilke data jeg må trekke ut strukturert, før jeg går over til å skrive og finpusse prompten. Da handler det om å liste opp helt vanlig engineering-arbeid, slik vi egentlig burde kjenne det fra før AI-æraen.

- Hvilke felt vil jeg trekke ut av de ustrukturerte dataene?
- Hvilke felt er obligatoriske? Hvilke er valgfrie?
- Hvilke verdiområder gjelder for tall og strenger? Finnes det enums?
- Hvor bør jeg begrense outputen, slik at den forblir brukbar i UI-et eller pipelinen?

Her hjelper ulike rammeverk meg, avhengig av programmeringsspråket jeg har valgt. Tar vi et av de mer moderne utviklingsmiljøene (TypeScript), kan for eksempel ai-sdk være aktuelt. Men også Java har sitt, med Spring AI, og andre programmeringsspråk har sikkert lignende verktøy. Disse rammeverkene hjelper med å samordne kommunikasjonen mot ulike modell-providere, så jeg ikke må binde meg direkte til leverandører og API-ene deres. I denne artikkelen konsentrerer jeg meg om TypeScript og ai-sdk.

<LinkCard url="https://spring.io/projects/spring-ai" />

Slike rammeverk har den store fordelen at de samordner API-ene til de enkelte leverandørene og gjør typiske funksjoner enkle og likeverdige å konfigurere - for eksempel structured outputs, akkurat det vi trenger.

<LinkCard url="https://ai-sdk.dev/docs/agents/building-agents#structured-output" />

For å konstruere denne contracten trengs det som regel en contract - først og fremst JSON-Schema. JSON-Schema beskriver contracten for JSON: Hvilke obligatoriske felt finnes? Hvilket regex må verdiene følge? Tallområder osv. - for å lage eller validere et slikt JSON-Schema kan vi bruke verktøy som [https://json.ophir.dev/](https://json.ophir.dev/). Eller spørre en AI om å lage et JSON-Schema som passer behovene våre.

> Den viktigste delen av AI-featuren min er ikke prompten, men kontrakten som resten av applikasjonen forventer av modellsvaret.

Med den genererte eller egenlagde contracten i bagasjen kan vi sette i gang med å formulere en passende prompt. Svaret vil helt sikkert enten følge contracten - eller en feil-contract som vi må håndtere separat, f.eks. `refusal` fra OpenAI.

<LinkCard url="https://developers.openai.com/api/docs/guides/structured-outputs" />

> Bygger du en AI-feature uten evals, tester du på brukerne.

40 linjer resultat. LGTM. Done.

Eller... ikke?

> Spørsmålet er ikke om svaret høres «smart» ut, men om det er pålitelig nok for workflowen min.

Hvordan vet jeg at resultatet er et godt resultat? Hvordan vet jeg at jeg kan stole på det? Contracten gir meg en strukturell garanti. Om innholdet holder faglig, er dermed ennå ikke besvart. Derfor er det først og fremst de faglige spørsmålene som må avklares: Er de berørte områdene fornuftig identifisert? Er risikoene brukbare? Kan jeg faktisk bruke testideene - eller er det unødvendig tull? Er approval-flagget plausibelt?
Én måte å besvare disse spørsmålene fullt ut på er å gå gjennom hvert eneste svar - og besvare og vurdere spørsmålene selv. Så kan jeg justere prompten og vurdere på nytt. Men min ærlige mening om det? Det vil jeg ikke, nei! Jeg gidder ikke.

Og ja, det finnes et alternativ. Faktisk flere. OpenAI har sin egen optimizer, men det finnes også mange open source-verktøy. Ett eksempel er [https://github.com/promptfoo/promptfoo](https://github.com/promptfoo/promptfoo).

<LinkCard url="https://developers.openai.com/api/docs/guides/prompt-optimizer" />

For å holde det enkelt valgte jeg OpenAI Platform her. Der er en evaluering raskt gjort: lag en prompt (viktig: med variabel!), opprett et nytt dataset under fanen *Evaluation*, og legg inn testdata. Jeg tar rett og slett noen av issuene mine fra bluelight-hub-prosjektet - deretter klikker du på play, og vips kjøres prompten på listen med inputs (obs: det koster penger).

Her får vi allerede mye hjelp fra OpenAI, nesten alt kan revideres automatisk direkte der, og også JSON-schemaet vårt kan genereres. Jeg limte rett og slett inn zod-schemaet fra eksempelprosjektet - og så ble det tilhørende JSON-schemaet generert... perfekt.

Grunnprinsippet bak evals burde likevel være tydelig: Definer mål, samle et datasett med eksempler og eventuelt forventede resultater, fastsett metrikker, sammenlign kjøringer, få dem evaluert.

## Observability i stedet for black box

Når vi bygger ikke-deterministiske systemer inn i applikasjonene våre, er det desto viktigere å forstå hva som skjedde når noe går i stykker, slik at vi finner en måte å forebygge akkurat det på. Til det hører noen viktige datapunkter som vi helst vil samle inn:

- hvilken modell ble brukt?
- hvor lang tid brukte LLM-en på et svar?
- var den returnerte JSON-en gyldig i henhold til contracten?
- var det nødvendig med retries?
- eventuelt: hvilke tools ble brukt?
- hvor måtte mennesker gripe inn?
- hvor mange tokens ble brukt, og hvor høye var kostnadene knyttet til dem?

OpenTelemetry har nå konvensjoner for GenAI-applikasjoner for events, metrikker og spans. Det betyr at også AI-funksjonene kan kobles inn i observability. AI SDK-et jeg nevnte over, har også en connector som automatisk samler inn og sender slike data via rammeverket.

## FullStack-delen er UI-et, ikke bare modellen

> Det blir først et FullStack-tema når jeg ikke bare snakker med en modell, men designer en brukerflyt for mennesker.

Nå som vi har avtalt en fornuftig contract med LLM-en, sender den over API-et og har bygget en virkelig god prompt - hva mangler? Klart, UI-et. I starten av innlegget antydet jeg det allerede: Å bare vise litt tekst, det kan alle. Selv etter one-shot-forsøket med Claude var det riktignok ikke et chatgrensesnitt, men likevel bare tekst etter tekst på rekke og rad. Vi beveger oss nok i litt tørt terreng her - en implementeringsplan for stories - men vi får vel til noe fint i alle fall når det gjelder visningen?
