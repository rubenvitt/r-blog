Most AI demos don't fail because of the model. They fail because they produce free text - when the application actually needs contracts. As soon as a model does more than answer nicely in a chat window and starts triggering product logic, good prompts alone aren't enough anymore.

AI full-stack engineering starts where model output becomes part of the system - that is, where I need a contract, evaluation and observability.

## The setup: our example

To make all of this a bit more concrete, I want to start with an example: a mini web app that turns a GitHub issue or any ticket text (e.g. from Jira or GitLab) into a structured implementation plan. For that, I start with a target structure that I'll use to explain an AI full-stack feature.

```json
{
  "summary": "string",
  "affectedAreas": ["frontend", "backend", "database", "infra"],
  "risks": ["string"],
  "implementationSteps": ["string"],
  "testIdeas": ["string"],
  "requiresApproval": true
}
```

With this structure in place, it's easy to have a web app generated that presents different implementation plans in a sensible way - in this case, Claude Code built it for me.

## Contract-first instead of prompt-first

For the example above, I simply had Claude build everything in one go - so technically, we're done here. The app works (based on a prompt ChatGPT wrote).

<Accordion title="Generated prompt used to build the demo">
You are a senior TypeScript engineer. Build a small but polished demo web app that showcases schema-first AI output using the Vercel AI SDK.

Do not ask follow-up questions.
Make reasonable choices and implement the full app end-to-end.
Do not leave placeholders or stubs.
Keep the code compact, readable, and suitable for a public demo repo / blog post.

Goal

Build a mini web app that turns either:

- freeform story / ticket text
- a GitHub issue

into a structured implementation plan.

The point of the app is to demonstrate that the AI feature is contract-first, not chat-first.

Stack

Use:

- Next.js App Router
- TypeScript
- AI SDK
- AI SDK UI
- Zod
- @ai-sdk/openai
- minimal styling only (simple CSS or Tailwind is fine)
- no database
- no authentication system
- no server-side persistence

Non-negotiable AI SDK architecture

Use these exact patterns:

- shared Zod schema imported by both client and server
- streamText + Output.object(...) in the route handler
- experimental_useObject on the client
- createOpenAI(...) to instantiate the provider with a request-specific API key
- custom request headers from the client to the analyze route
- no plain-text fallback mode for the main analysis flow
- do not use useChat for the main experience

This app is object-generation first, not chat first.

Core JSON contract

The app must use this exact top-level JSON shape and these exact property names:

{`{
"summary": "string",
"affectedAreas": ["frontend", "backend", "database", "infra"],
"risks": ["string"],
"implementationSteps": ["string"],
"testIdeas": ["string"],
"requiresApproval": true
}`}

Implement it as a shared Zod schema and export the inferred TypeScript type.

Schema requirements:

- summary: non-empty string
- affectedAreas: non-empty array of unique enum values, restricted to: frontend, backend, database, infra
- risks: array of strings
- implementationSteps: non-empty array of strings
- testIdeas: non-empty array of strings
- requiresApproval: boolean

Do not parse model text with regex.
Do not accept "almost matching" output.
The UI and server must rely on schema-validated structured output.
</Accordion>

But let's take a few steps back. Normally, I don't build something just to fill it with AI. Instead, I want my data processed and integrated into the UI in a smart way. There are countless articles about that online already, and AI handles that part for me just fine.

The core point, though, is this: the contract comes first, then the prompt. I need to know what data I have to extract in structured form before I move on to writing and polishing my prompt. That means doing the kind of engineering groundwork we already knew from the pre-AI era.

- Which fields do I want to extract from the unstructured data?
- Which fields are required? Which are optional?
- What value ranges apply to numbers and strings? Are there enums?
- Where should I limit the output so it stays usable in the UI or the pipeline?

Depending on the programming language, different frameworks help with this. In one of the more modern ecosystems like TypeScript, the AI SDK is an obvious candidate. Java has Spring AI, and other languages surely come with similar tooling. These frameworks unify communication with different model providers, so I don't have to tie myself directly to vendors and their APIs. In this article, I'm focusing on TypeScript and the AI SDK.

<LinkCard url="https://spring.io/projects/spring-ai" />

The big advantage of frameworks like these is that they unify the individual providers' APIs and make common features easy to configure the same way everywhere - structured outputs, for example, which is exactly what we need.

<LinkCard url="https://ai-sdk.dev/docs/agents/building-agents#structured-output" />

To build this contract, you usually need a schema - mostly JSON Schema. A JSON Schema describes the contract for a piece of JSON: which fields are required? What regex do their values have to match? Number ranges, and so on. To create or validate a JSON Schema, we can use tools like [https://json.ophir.dev/](https://json.ophir.dev/). Or ask an AI to create a JSON Schema that fits our needs.

> The most important part of my AI feature isn't the prompt, it's the contract the rest of the application expects from the model's response.

With the contract in hand, generated or hand-written, we can get to work on a matching prompt. The response will then either match the contract - or an error contract we have to handle separately, e.g. OpenAI's `refusal`.

Or... not?

> The question isn't whether the answer sounds "smart", it's whether it's reliable enough for my workflow.

How do I know the result is a good result? How do I know I can trust it? The contract gives me a structural guarantee. Whether the content holds up is a different question entirely. So the questions that matter most are about the substance: were the affected areas identified sensibly? Are the risks useful? Can I actually use the test ideas - or is it pointless nonsense? Is the approval flag plausible?
One way to answer these questions thoroughly is to go through every single response - and answer and rate them myself. Then I can adjust the prompt and rate again. But my honest opinion on that? I don't want to, no! I really can't be bothered.

And yes, there is an alternative. Several, actually. OpenAI has its own optimizer, but there are also plenty of open-source tools. One example would be [https://github.com/promptfoo/promptfoo](https://github.com/promptfoo/promptfoo).

<LinkCard url="https://developers.openai.com/api/docs/guides/prompt-optimizer" />

To keep the demonstration simple, I went with the OpenAI Platform here. An evaluation is set up quickly there: create a prompt (important: with a variable!), create a new dataset in the *Evaluation* tab, then add test data. I simply grab a few of my issues from the bluelight-hub project - then click play, and the prompt runs against the list of inputs (careful: this costs money).

OpenAI already helps a lot here; almost everything can be revised automatically right there, and our JSON Schema can be generated too. I just pasted the Zod schema from the example project in there - and it generated the matching JSON Schema.... perfect.

But the basic principle of an eval should be clear by now: define goals, collect a dataset from examples and possibly expected results, set metrics, compare runs, have them evaluated.

## Observability instead of a black box

When we build non-deterministic systems into our applications, it's all the more important to understand what happened when something breaks, so we can find a way to mitigate exactly that. That takes a few important data points we ideally want to collect:

- which model was used?
- how long did the LLM take to respond?
- was the returned JSON valid against the contract?
- were retries needed?
- if applicable: which tools were used?
- where did humans have to step in?
- how many tokens were used, and what did they cost?

OpenTelemetry now has conventions for GenAI applications covering events, metrics and spans. That means AI features can be wired into observability as well. The AI SDK mentioned above also has a connector that captures and exports this data automatically through the framework.

## The full-stack part is the UI, not just the model

> It only becomes a full-stack topic when I'm not just calling a model but designing an interaction flow for humans.

So we've agreed on a reasonable contract with the LLM, we communicate it via the API, and we've built a really great prompt. What's missing? Right, the UI. At the start of the post I already hinted at it: anyone can just display a bit of text. Even after the one-shot attempt with Claude, it wasn't a chat interface, but it was still just text after text.
