## Die Vorbereitung: Unser Beispiel

## Contract-first statt Prompt-first

Mit dem Beispiel von oben hab ich Claude einmal alles bauen lassen - eigentlich sind wa hier schon fertig. Die App funktioniert (nach 'nem Prompt, den ChatGPT geschrieben hat). Feierabend? Nich ganz.

<Accordion title="Generierter Prompt zum Bauen vonne Demo">
You are a senior TypeScript engineer. Build a small but polished demo web app that showcases schema-first AI output using the Vercel AI SDK.

Do not ask follow-up questions.
Make reasonable choices and implement the full app end-to-end.
Do not leave placeholders or stubs.
Keep the code compact, readable, and suitable for a public demo repo / blog post.

Goal

Build a mini web app that turns either:

- freeform story / ticket text
- a GitHub issue

into a structured implementation plan.

The point of the app is to demonstrate that the AI feature is contract-first, not chat-first.

Stack

Use:

- Next.js App Router
- TypeScript
- AI SDK
- AI SDK UI
- Zod
- @ai-sdk/openai
- minimal styling only (simple CSS or Tailwind is fine)
- no database
- no authentication system
- no server-side persistence

Non-negotiable AI SDK architecture

Use these exact patterns:

- shared Zod schema imported by both client and server
- streamText + Output.object(...) in the route handler
- experimental_useObject on the client
- createOpenAI(...) to instantiate the provider with a request-specific API key
- custom request headers from the client to the analyze route
- no plain-text fallback mode for the main analysis flow
- do not use useChat for the main experience

This app is object-generation first, not chat first.

Core JSON contract

The app must use this exact top-level JSON shape and these exact property names:

{`{
"summary": "string",
"affectedAreas": ["frontend", "backend", "database", "infra"],
"risks": ["string"],
"implementationSteps": ["string"],
"testIdeas": ["string"],
"requiresApproval": true
}`}

Implement it as a shared Zod schema and export the inferred TypeScript type.

Schema requirements:

- summary: non-empty string
- affectedAreas: non-empty array of unique enum values, restricted to: frontend, backend, database, infra
- risks: array of strings
- implementationSteps: non-empty array of strings
- testIdeas: non-empty array of strings
- requiresApproval: boolean

Do not parse model text with regex.
Do not accept "almost matching" output.
The UI and server must rely on schema-validated structured output.
</Accordion>

Gehen wa aber noch ma 'n paar Schritte zurück. Normalerweise bau ich nich wat, bloß um et mit AI vollzukippen. Stattdessen sollen meine Daten aufbereitet und schlau inne UI eingebaut werden. Dazu gibt et schon unzählige Artikel im Internet, und AI hilft mir da schon prima.

Der Knackpunkt is aber: Zuerst kommt der Contract, dann der Prompt. Ich muss wissen, welche Daten ich strukturiert rausziehen muss, bevor ich mich ans Schreiben und Polieren von meinem Prompt mach. Dafür heißt et, Engineering-Arbeit aufzulisten, wie man se schon vor der AI-Zeit kennen sollte.

- Welche Felder will ich aus den unstrukturierten Daten rausziehen?
- Welche Felder sind Pflicht? Welche optional?
- Welche Wertebereiche gelten für Zahlen & Strings? Gibt et Enums?
- An welchen Stellen sollt ich den Output begrenzen, damit der inne UI oder Pipeline brauchbar bleibt?

Dabei helfen mir je nach Programmiersprache unterschiedliche Frameworks. Nehmen wa eine vonne moderneren Entwicklungsumgebungen (TypeScript), dann käm zum Beispiel ai-sdk in Frage. Aber auch Java wird mit Spring AI bedient, andere Programmiersprachen bringen bestimmt ähnliches Werkzeug mit. Diese Frameworks helfen, die Kommunikation mit verschiedenen Model Providern zu vereinheitlichen, sodass ich mich nich direkt an Hersteller und deren APIs ketten muss. In diesem Artikel bleib ich bei TypeScript & ai-sdk.

<LinkCard url="https://spring.io/projects/spring-ai" />

Solche Frameworks haben den dicken Vorteil, dat se die APIs vonne einzelnen Anbieter vereinheitlichen und typische Funktionen einfach und gleich konfigurierbar halten - so z.B. structured outputs, genau dat, wat wa brauchen.

<LinkCard url="https://ai-sdk.dev/docs/agents/building-agents#structured-output" />

Um diesen Contract zu bauen, brauchse meistens 'n Contract - vor allem JSON-Schema. JSON-Schemas beschreiben den Contract für JSONs: Welche Pflichtfelder gibt et? Welchen Regex müssen die Werte einhalten? Zahlenbereiche usw. - um so'n JSON-Schema zu bauen oder zu prüfen, können wa Tools wie [https://json.ophir.dev/](https://json.ophir.dev/) nehmen. Oder die AI fragen, ob se uns 'n passendes JSON-Schema nach unseren Wünschen baut.

> Dat Wichtigste an meinem AI-Feature is nich der Prompt, sondern der Vertrag, den der Rest vonne Anwendung vonne Modellantwort erwartet.

Mit dem generierten oder selbst gebauten Contract im Henkelmann können wa uns aufmachen, 'n passenden Prompt zu schreiben. Die Antwort wird dann entweder dem Contract entsprechen - oder 'nem Fehler-Contract, um den wa uns extra kümmern müssen, z.B. `refusal` von OpenAI.

> Wer 'n AI-Feature ohne Evals baut, testet am Nutzer.

40 Zeilen Ergebnis. LGTM. Done. Ab anne Bude.

Oder... doch nich?

> Die Frage is nich, ob die Antwort "smart" klingt, sondern ob se für meinen Workflow verlässlich genug is.

Woher weiß ich, dat dat Ergebnis 'n gutes Ergebnis is? Woher weiß ich, dat ich mich da drauf verlassen kann? Der Contract gibt mir 'ne strukturelle Garantie. Ob der Inhalt fachlich wat taugt, is damit noch nich beantwortet. Deswegen müssen vor allem die fachlichen Fragen geklärt werden: Sind die betroffenen Bereiche vernünftig erkannt? Sind die Risiken brauchbar? Kann ich mit den Testideen wirklich wat anfangen - oder is dat überflüssiger Kokolores? Is dat Approval-Flag plausibel?
Eine Möglichkeit, diese Fragen komplett zu beantworten, is, durch jede einzelne Antwort durchzugehen - und die Fragen für mich selber zu beantworten, zu bewerten. Dann kann ich den Prompt anpassen und noch ma bewerten. Aber meine ehrliche Meinung dazu? Dat will ich nich, nee! Da hab ich keinen Bock drauf.

Und jau, et gibt 'ne Alternative. Sogar 'n paar. OpenAI hat 'n eigenen Optimizer, et gibt aber auch jede Menge Open-Source-Tools. 'n Beispiel dafür wär [https://github.com/promptfoo/promptfoo](https://github.com/promptfoo/promptfoo).

Da is 'ne Evaluierung flott gemacht: Prompt anlegen (wichtig: mit Variable!), im Reiter *Evaluation* 'n neues Dataset anlegen, dann Testdaten reinkippen. Ich nehm mir einfach 'n paar von meinen Issues ausm bluelight-hub-Projekt - danach auf Play klicken, schon wird der Prompt auf die Liste an Inputs losgelassen (Achtung: kostet Geld).

Hier hilft uns OpenAI schon ordentlich, fast alles kann da direkt automatisch überarbeitet werden, auch unser JSON Schema kann generiert werden. Ich hab einfach ma dat zod-Schema ausm Beispielprojekt da reingepackt - dann wurde dat passende JSON Schema dazu generiert.... perfekt.

## Observability statt Black Box

Wenn wa nichtdeterministische Systeme in unsere Anwendungen einbauen, is et umso wichtiger zu verstehen, wat passiert is, wenn ma wat kaputt is, damit wa 'n Weg finden, genau dat abzumildern. Dazu gehören 'n paar wichtige Datenpunkte, die wa am besten sammeln:

- welches Modell wurde genommen?
- wie lange hat dat LLM für 'ne Antwort gebraucht?
- war dat zurückgegebene JSON valide zum Contract?
- waren Retries nötig?
- ggf.: welche Tools wurden benutzt?
- wo mussten Menschen eingreifen?
- wie viele Token gingen drauf und wat hat dat gekostet?

OpenTelemetry hat inzwischen Konventionen für GenAI Applications für Events, Metriken & Spans. Dat heißt, auch die AI-Funktionen können in die Observability eingebunden werden. Im oben erwähnten AI SDK gibt et ebenfalls 'n Konnektor, um über dat Framework automatisch die passenden Daten aufzunehmen und zu verschicken.
