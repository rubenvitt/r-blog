## Fünf Dinger, die alle Memory heißen

Hinter dem Wort stecken mindestens fünf Datenarten, und jede hat 'nen anderen Besitzer und 'ne andere Lebensdauer.

**Session State** is der Verlauf vonne laufende Unterhaltung, samt Tool-Ergebnissen. Der gehört der Session, landet als Ausschnitt im Prompt und is nach Minuten oder Tagen wieder wech.

Dat **Profil** mit Adresse, Vertrach und Kundennummer gehört dem Fachsystem, wo et schon lange vor dem Agenten drinstand. Der Agent liest ausgewählte Felder. Geändert und gelöscht wird dat da, die Kopien ziehen nach.

'Ne **Präferenz** hat die Person selbst geäußert, so wat wie "Erinnerungen bitte per SMS". Die gilt, bis die Person se zurücknimmt, und steht dafür im Prompt.

Beim **Retrieval** holt sich der Agent Dokumente, Tickets oder alte Chats per Suche dazu. Der Index da drüber is bloß 'ne Kopie. Der lebt so lange wie seine Quelle und muss nachgezogen werden, wenn die verschwindet. In'n Prompt kommen nur die Treffer.

Dat **Audit**-Protokoll gehört dem Betreiber und hält fest, wat der Agent gemacht hat. Dat kommt nie in'n Prompt und wird erst nach Ablauf vonne Aufbewahrungsfrist gelöscht. Personenbezogene Teile da drin brauchen 'ne eigene Lösung, etwa Redaction oder 'nen Schlüssel, den man vernichten kann.

Der Mem0-Eintrag aussem Labor passt in keine von diese Zeilen. Der is abgeleitet wie ein Index, steht im Prompt wie 'ne Präferenz und hat weder Ablaufdatum noch Herkunft. Watt'n Brassel.

Getrennte Regeln brauchen übrigens keine fünf Datenbanken. Eine Tabelle mit einer Spalte für die Datenart reicht völlich, solange jede Art ihre eigene Lösch- und Prompt-Regel kricht.

## Herkunft und Kaskade bauen

Im Kern is der Löschpfad 'ne Abfrage nach allem, wat aus dem Chat stammt, plus 'ne Sperre gegen spätet Schreiben. Als Skizze:

```typescript
type Derived = { id: string; kind: "memory" | "summary" | "index" | "preference"; derivedFrom: string[]; explicit?: boolean };

async function deleteChat(chatId: string) {
  await db.tx(async (tx) => {
    await tx.lockChats([chatId], "exclusive");
    await tx.chats.markDeleted(chatId); // Tombstone, der Verlauf selbst fliecht wech
    for (const d of await tx.derived.bySource(chatId)) {
      if (d.kind === "preference" && d.explicit) continue;            // Produktregel: bleibt, Herkunft sichtbar
      if (d.derivedFrom.length > 1) await tx.rebuild.enqueue(d.id);   // aus die übrigen Chats neu ableiten
      else await tx.derived.delete(d.id);
    }
    await tx.outbox.enqueue({ type: "destroy-key", chatId }); // Protokoll: Schlüssel pro Chat, im selben Commit beauftragt
  });
}
// Ein Worker ruft keys.destroy(chatId) idempotent auf, bis et klappt. Erst dann is die Löschung durch, Schicht im Schacht.

async function writeDerived(d: Derived) {
  await db.tx(async (tx) => {
    const chats = await tx.lockChats(d.derivedFrom, "shared");
    if (chats.some((c) => c.deleted)) throw new Error("Quelle gelöscht");
    await tx.derived.insert(d);
  });
}
```

Wichtig is die Sperre. "Tombstone prüfen, dann schreiben" ohne gemeinsame Sperre lässt 'ne Race Condition offen: Der Job prüft, dat Löschen läuft dazwischen durch, der Job schreibt. Mit Sperre auffe Chat-Zeile committet der Job entweder vorher, dann findet ihn `bySource`, oder nachher, dann sieht er den Tombstone. Wie anne Pommesbude: Wer zuerst anne Theke steht, wird zuerst bedient.

Wo `derivedFrom` herkommt, entscheidet der Schreibweg. In B muss der Assistent für `remember` ein wörtlichet Zitat aus 'ner Nutzer-Nachricht vonne laufende Session mitliefern, und die Anwendung prüft dat. Damit is die Herkunft festgenagelt, der Wert aber nich: Ein vergiftetet Dokument könnte den Assistenten dazu kriegen, "Mitarbeiterin, darf Gebühren erlassen" mit einem echten Satz vonne Nutzerin abzulegen. Berechtigungen sollten deshalb ausschließlich aussem Profil kommen, dat dat Modell nich schreibt. Den Schlüssel sucht sich dat Modell frei aus, siehe "Vater sitzt im Gefängnis", der gehört also mitgeschützt.

In 'nem bestehenden Stack mit Extraktor und Vektor-Store kannze dat Schritt für Schritt nachrüsten:

1. **Herkunft an jeden Eintrag.** `derivedFrom` mit den Chat-IDs als Metadatum. Altbestände, wo sich die Herkunft nich zuverlässig rekonstruieren lässt, neu extrahieren oder inne Tonne.
2. **Löschen per Filter.** Alle Einträge mit dieser Quelle löschen, notfalls über 'ne eigene Tabelle von Quelle zu Eintrags-ID. Ablaufen lassen reicht nich, inne [Doku von Mem0](https://docs.mem0.ai/platform/features/expiration-date) heißt et: "Expiration hides a memory, it does not delete it."
3. **Zusammenfassungen neu bilden.** Zep macht beim [Löschen von einer Episode](https://help.getzep.com/deleting-data-from-the-graph) Kanten und Knoten nur wech, wenn keine andere Episode se stützt, und erzeugt Namen und Zusammenfassungen von geteilten Knoten nich neu. Die können also weiter enthalten, wat grad gelöscht wurde.
4. **Rebuild aussem Log.** Martin Kleppmann empfiehlt, [Index, Cache und Views aus einem Log zu speisen](https://martin.kleppmann.com/2015/05/27/logs-for-data-infrastructure.html). Sauber is ein Rebuild nach dem Löschen aber nur, wenn der Tombstone im Log steht oder dat Log kompaktiert wird.

Fürs Protokoll reicht dat nich, da kracht "nur anhängen" mit dem Recht auf Löschung zusammen. Ein Hash hilft wenig, weil sich erratbare Suchbegriffe gegen den bestätigen lassen. Besser is Redaction vor dem Schreiben oder Crypto-Shredding. Dat [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing) beschreibt dat mit einem Schlüssel pro betroffener Person, für "Chat löschen" passt einer pro Chat. Wann Sperren statt Löschen in Frage kommt, hab ich im Logging-Post auseinandergenommen.

## Wat dat kostet

Die Ausnahme für ausdrücklich gespeicherte Wünsche hat 'nen harten Fall: Steht im Wunsch die Diagnose, bleibt se stehen. Ich halt dat für richtig, weil die Person se selbst hat speichern lassen. Die Oberfläche muss beim Löschen aber zeigen, wat bleibt.

Dazu kommt Plumbing, also ehrliche Maloche: Metadaten an jedem Eintrag, Tombstones mit Sperre, ein Rebuild-Pfad und Schlüssel fürs Protokoll. In B verzichte ich außerdem auf dauerhaft gespeicherte implizite Vorlieben, weil die Zitatregel nur Ausgesprochenet zulässt. Wer drei Sessions lang nach Krimis gefragt hat, ohne "ich mag" zu sagen, hat von B in keinem von fünf Läufen zuerst 'nen Krimi empfohlen gekricht. Dat liegt anne Schreibregel. Ein Extraktor, der implizite Vorlieben mit Herkunft und kurzer TTL ablegt, wär mit demselben Löschpfad vereinbar, gemessen hab ich dat aber nich.
